## これはなに

Nstock株式会社でソフトウェアエンジニアをしているnonoです。主に携わっているNstock株式報酬のバックエンドサービスにNullAwayを導入しました。

不確実なNullabilityはレビューコストを常に引き上げる方向に働きます。NullAwayはアノテーションベースに静的解析を行ない、不適切な取り扱いをコンパイルエラーとして検出します。これによりJavaでもnull-safeな言語のように実装できます。コードの実装コストが低廉化した現在において、受入のコストを下げる重要度は高いと考えて導入しました。

NullAwayを設定だけ導入することは簡単です。難しいのは、既存コードのNullabilityを棚卸しし、確かな根拠を見つけ、なければ生み出し、それを実装に固定していく作業でした。この記事では、Nullabilityをどのように確かめ、どの順で積み上げたのかを話します。

:::message
Mavenの基本的な記述方法は理解されている方向けに、主としてはスコープ設定、マイルストーン分割、個別のハマりどころと解決アプローチについて記述します。
:::

## NullAwayとは？なぜ今入れるのか

NullAwayはUberが開発したError Proneプラグインです。アノテーションベースに静的解析を行ない、 `@Nullable` が宣言されていない箇所へのNullの代入や、Nullableな値の未チェックの参照をコンパイル時点で検出できます。

https://github.com/uber/nullaway

NullとJavaユーザーの格闘は長く、NonNull/Nullableを表現するアノテーションも複数存在します。そんな中、昨年リリースされたSpring Framework 7では、それまで活用されていた `org.springframework.lang.NonNull` がDeprecatedとなり、 `org.jspecify.annotations` 系のアノテーションが標準採用されました。

JSpecifyはJavaの静的解析アノテーションの標準化を進めるオープンソースプロジェクトです。

https://jspecify.dev/

元からNullAwayはアノテーション名の単純一致で検証を行なうため、`org.springframework` 由来のアノテーションも検証可能でした。Spring Framework 7での標準対応により、Springに限らず依存ライブラリ群も含めてNullability系アノテーションの取り扱いを一本化できる機運が生じました。そこで改めて導入を検討するに至りました。

まとめると、NullAwayはあくまで「Nullabilityを正しくハンドリングできていることを静的解析により保証するツール」です。宣言に反する取り扱いは、コンパイルという必ず通るゲートで検出されます。そのため、一度宣言したNullabilityは実装から乖離しないまま維持されます。

これにより、Nullabilityに関わる実装の妥当性を保証し続けられます。一方で、「何をNullableとみなすのか」は利用者が定義する必要があります。

## 導入計画

### 導入方法

基本的にはpom.xml（またはbuild.gradle）にNullAwayとError Proneの設定を追加すれば動作します。

```xml:pom.xml
<dependencies>
  <!--
    JSpecify のアノテーション（@NullMarked / @Nullable）。
    Spring Boot の依存管理（spring-boot-starter-parent、または spring-boot-dependencies の
    import）を利用している場合、バージョンは BOM 側で管理されるため <version> の指定は不要。
    provided ではなく compile スコープにする。@NullMarked は RUNTIME 保持のため、
    provided にするとランタイムでクラスロードエラーになりうる。
    Error Prone / NullAway 自体はソースから参照しないので dependencies には不要。
  -->
  <dependency>
    <groupId>org.jspecify</groupId>
    <artifactId>jspecify</artifactId>
    <version>1.0.1</version>
  </dependency>
</dependencies>

<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
      <configuration>
        <!-- 後述の -J 引数をコンパイラ JVM に渡すために必須。fork しないと無視される -->
        <fork>true</fork>
        <annotationProcessorPaths>
          <path>
            <groupId>com.google.errorprone</groupId>
            <artifactId>error_prone_core</artifactId>
            <version>2.50.0</version>
          </path>
          <path>
            <groupId>com.uber.nullaway</groupId>
            <artifactId>nullaway</artifactId>
            <version>0.14.1</version>
          </path>
        </annotationProcessorPaths>
        <compilerArgs>
          <!-- Error Prone が javac 内部 API を触るための export 設定（JDK 16 以降で必要） -->
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.api=ALL-UNNAMED</arg>
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.file=ALL-UNNAMED</arg>
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.main=ALL-UNNAMED</arg>
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.model=ALL-UNNAMED</arg>
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.parser=ALL-UNNAMED</arg>
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.processing=ALL-UNNAMED</arg>
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.tree=ALL-UNNAMED</arg>
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.util=ALL-UNNAMED</arg>
          <arg>-J--add-opens=jdk.compiler/com.sun.tools.javac.code=ALL-UNNAMED</arg>
          <arg>-J--add-opens=jdk.compiler/com.sun.tools.javac.comp=ALL-UNNAMED</arg>
          <!-- Error Prone に必要なコンパイラポリシー設定 -->
          <arg>-XDcompilePolicy=simple</arg>
          <arg>--should-stop=ifError=FLOW</arg>
          <!-- Error Prone の他チェックは全て無効化し、NullAway だけを ERROR で有効化する -->
          <arg>-Xplugin:ErrorProne -XepDisableAllChecks -XepOpt:NullAway:AnnotatedPackages=jp.nstock.backend -XepOpt:NullAway:JSpecifyMode=true -Xep:NullAway:ERROR</arg>
        </compilerArgs>
      </configuration>
    </plugin>
  </plugins>
</build>
```

またはmaking氏の nullability-maven-plugin を利用する方法もあります^[私たちは2025/11頃から検証を始めておりタイミングが合いませんでした]。

### ゴールをどこに設定するか

NullAway + Error Proneの構成では、パッケージ単位で段階的にNullAwayの導入を進めることができます。
```xml:pom.xml
<!-- OnlyNullMarked=true: @NullMarked が付いたパッケージだけをチェック対象にする -->
<arg>-Xplugin:ErrorProne -XepDisableAllChecks -XepOpt:NullAway:OnlyNullMarked=true -XepOpt:NullAway:JSpecifyMode=true -Xep:NullAway:ERROR</arg>
```
```java:package-info.java
@NullMarked
package jp.nstock.backend.command.stock_option.domain;

import org.jspecify.annotations.NullMarked;
```
これにより、NullAwayをどこまで入れるのか、という意思決定が可能になります。

方針の候補は以下の2つでした。
1. コアドメインにのみ導入する
2. プロジェクト全体を対象とする

1はROIベースでは良好な選択肢と言えるでしょう。変更頻度が高く、重要な箇所にのみ絞って導入する。一方で、私たちは2の方針で進めることとしました。決め手はレビューコストの観点でした。

値にNullが入りうると、レビュー時にトレースすべき値の範囲は広がります。AI支援などでコードの実装コスト自体が低廉化した現代において、受入のコストを下げる価値は高まっていると考えました。また部分的な導入は、その境界を意識したレビューが必要になります。これはレビューの認知負荷を高める方向に働き、望ましくないと判断しました。

:::message
後述の通り、結論としてはプロジェクト全体を網羅的に、遺漏なく検証対象にしたわけではありません。
テストコードや、生成コード（の内部実装）などは検証対象外としています。

ふりかえると結論としては、混在しやすい機能実装の中に境界を設けるのではなく、技術的に隔離しやすい外部との間に境界を設ける方を選んだ、と言えるでしょうか。
:::

### 具体的な方針の検討

NullAwayをいきなりプロジェクト全体に適用するのは現実的ではありませんでした。

導入時点で `@NonNull` `@Nullable` のようなアノテーションは部分的に設定されていましたが完全ではありませんでした。この状況で設定を導入すると、まず「見過ごされていたがNullableな値をNonNullに渡そうとしている」箇所がコンパイルで落ちます。当時の環境でプロジェクト全体に設定を適用した場合を実測すると、520箇所、155ファイルでコンパイルエラーが発生しました。

コンパイルを通すためには値の出元をNonNullでアノテーションするか、`Objects.requireNonNull` で囲うかしてNonNullを保証する必要があります。値が一貫してNonNull保証できるなら簡単ですが、ユースケース固有のNonNull性であれば `Objects.requireNonNull` が必要であり、調査に誤りがあれば実行時エラーとなります。NonNullを保証できる型とNullableな型を同じClassで取り扱うことがそもそも不適切で、分離すべきという箇所もあるでしょう。

また設定済みのNonNull、Nullableがどこまで信用できるのか、という問題もあります。当初の想定ではNonNullだったが、機能拡張の過程でNullを取り扱う経路が増え、アノテーションがメンテナンスされていないケースもありえます。

そのため大方針としては、Nullabilityの確かな根拠を持てる箇所から段階的に導入していくことにしました。具体的には、infrastructure -> domain -> presentation -> usecase層の順です^[実際には特定のコア機能を代表値としてinfrastructure + domain層に関して技術検証を行なってから水平展開に進んでいます。]。

## 導入実践

### infrastructure層の実装

infrastructure層の実装の大半はDBアクセスでした。従ってNullabilityの根拠はDBスキーマから得ることができます。カラム定義にnot null制約が設定された列の参照は確実にNonNullであると言えます。

対象プロジェクトではSpring Data JDBCを利用しており、 `@Table` を用いてテーブルと紐づくDTOを作成して持ち回る実装が大半を占めていました。そのため、infrastructure層のDTO群のNonNull/Nullableは確度高く整備できました。

考慮が必要だったのは以下のようなケースです。
1. 読み書きで同一のModelを利用していたため、参照時はNonNullだが書き込み時にはNullableのような箇所がある（e.g. DB採番を行なうID列等）。これらは個別に評価してNullable Markを付与しました。
2. 外部結合によりNullabilityが発生しうるケース。これは機械的には判断できないため、個別データのライフサイクルからNullが正常系であり得るかデータ不整合の異常系かの整理をつけていく作業が必要でした。

### domain層の実装

domain層はModel側で不変条件としてNull検証している箇所が多く、これも確度が高いNullabilityの根拠として利用できました。

また上述のパッケージ構成により、infra + domainは機能パッケージとして独立していました。これにより影響範囲を抑えて個別に対応が進めやすかったのも、次にdomain層に着手した理由の1つです。domain層をこのタイミングで適用するか、presentation層が片付いてからusecaseと合わせて対応するかはプロジェクト構成や各層の厚みに依存する箇所でしょう。

### presentation層の実装

presentation層のNullabilityの根拠としては、クライアントとの契約（API定義）を採用したかったのですが、簡単にはいきませんでした。

presentation層は主にWeb API実装を行なっています。対象プロジェクトではOpenAPI Specification + OpenAPI Generatorを用いて開発を行なっています。specにはrequiredを付与していましたが、歴史的経緯からあまり信頼しきれない状態となっていました。

またNullAwayとは別の文脈でも、既存のspecの構成に課題が溜まっている状態でした。
1. URLパスの第1階層でController Classを分割していたため、一部Controllerが肥大していた（最も肥大したコントローラのテストクラスで15k行近く）
2. 歴史的経緯から記法がブレている。requiredの設定方針、exampleの有無、Enumの定義をschemaと同一ファイルに書くか・ファイルを分けるか など
3. OpenAPI specで定義したEnumがpresentation層以外でも利用されている。これにより、Web API利用者に向けた表現幅とドメインの表現幅（場合によってはDBの表現幅）が乖離できない箇所があった

上記が積もり積もったこともあり、NullAway対応を契機にAPIを全て（180エンドポイント程度）作り直すこととしました。具体的には以下のような仕組みを整備した上で、個別エンドポイントの移行を順次進めました。

1. OpenAPIの記法についてガイドドキュメントを整備。合わせてマージ前に検証を行なうCIをspectralを用いて実装。
2. 新規specの生成物の配置先にpackage-info.javaを配置してNullAway対象化
3. 新規specの生成物の配置先に対する依存をpresentation層からのみ許可するようArchUnitのRule整備

またOpenAPI Generatorによって出力するNullabilityアノテーションを `importMapping` でJSpecify由来のものに固定しています。

```xml:pom.xml（該当箇所のみ抜粋）
<execution>
    <id>generate-v2-admin</id>
    <goals>
        <goal>generate</goal>
    </goals>
    <configuration>
        <importMappings>
            <importMapping>Nullable=org.jspecify.annotations.Nullable</importMapping>
        </importMappings>
    </configuration>
</execution>
```

これにより、新規の生成物の記法を揃えつつ、NullAwayの検証を成立させつつ、ArchUnitで弾かれる箇所を修正することで求める状態に近づけられるようガードレールを敷きました。そのうえで個別エンドポイントについてフロントエンドのハンドリングを調査し、Nullが設定されうる箇所のみrequiredを外す、という地道な移行を行ないました。

まとめるとpresentation層では、以下のような構成でNullabilityを検証しています。
1. OpenAPI specのrequiredを中核とし、生成Modelに対しアノテーションを付与する。
2. Controller以降のハンドリングは生成Modelに対して付与されたNullabilityの宣言を信頼し、NullAwayがそれを保証する。
3. リクエスト受信時においてrequiredがnon-nullであることはBeanValidationが保証する。

### usecase層の実装

usecase層には強いNullabilityの根拠がありません。そのため最後に着手することになりました。

usecase層に内在する根拠がなくとも、inとoutのNullabilityが定まった状態まで来てしまえば後は挟み込みです。周辺コードは既にNullabilityが保証されているので、整合するように必要な箇所にアノテーションを付与していく作業となります。また関数内で新たな値を作り出す箇所のNullabilityは比較的狭い範囲の調査で絞り込めます。

### プロダクションコード全体への適用と一部除外

ここまでで各パッケージに対しての整備が完了したので、改めて段階導入の為の仕組みを撤去して、プロダクションコード全体へ設定を適用します。具体的にはpom.xmlの検査範囲変更（ `OnlyNullMarked` から `AnnotatedPackages` への切替）と、NullMarkedしか持たないpackage-info.javaの削除です。

一方で単に除外したわけではなく、以下のような点への対処を行ないながら進めました。
* Spring DataのRepositoryは単件取得のIFにおいて戻り値に非Optionalを利用していた場合、該当なしの場合Nullを返します。Spring Dataの `NullnessMethodInvocationValidator` はpackageのNullMarkedを参照して実行時検証を行ないますが、package-info.javaを削除すると、これが失われた状態となります。幸い、既存の実装では全て `Optional` を利用する実装方針だったため、プロダクションコードの変更は不要でした。単件取得はOptionalで返すことを強制するArchUnitルールを追加して手当てとしました。
* Jilt、OpenAPI Generator等の生成コードの内部実装については、検出しても対処が困難であり、また検査するモチベーションもありません。NullAwayでは未アノテーションを示す `UnannotatedSubPackages` と、内部実装について検証を行なわない `ExcludedClassAnnotations` が分離されています。後者を用いて内部実装については検証せず、一方でインターフェースのNullabilityを伝播させる作りとしました。
* テストコードは検証対象外としました。Nullabilityを検査・修正するモチベーションが高くなく、修正コストに対して得られるものが少ないと判断しました。具体的には `testCompile` 時に `-Xplugin` を明示的に渡さないことで検証対象外としています。

それらをまとめた最終的な設定argは以下のようになります。

```xml:pom.xml
<!--
  段階導入用の OnlyNullMarked を AnnotatedPackages に置き換え、パッケージ単位の宣言を不要にする。
  ExcludedClassAnnotations は生成コードの「内部実装の検査」だけを外す設定で、
  シグネチャの nullability 宣言は呼び出し側から見えたまま残る。
-->
<arg>-Xplugin:ErrorProne -XepDisableAllChecks -XepOpt:NullAway:AnnotatedPackages=jp.nstock.backend -XepOpt:NullAway:JSpecifyMode=true -XepOpt:NullAway:ExcludedClassAnnotations=javax.annotation.processing.Generated,org.jilt.JiltGenerated,jakarta.annotation.Generated -Xep:NullAway:ERROR</arg>
```

## 進め方の工夫

全体を通して作成されたPR本数は199本、うち仕組みの構築は19本で残る180本が移行作業でした^[diffでは +186,732 / -200,820 になりました]。これらのうち197本は筆者が作成していますが、機能開発をメインで担当しながら、サイドプロジェクトとして進行しました。

ここまで見ていただいたように、確認観点や行なうべき作業はレイヤーごとに手順化できます。そのためレイヤーに対応したskillsを作成して、Draft PRの作成までは自走できるようにしました。人間の手や、Agentの利用枠等に余裕があるタイミングがあればAgentにPR作成を進めてもらい、後は人間が受け入れに集中するという体制を構築できました。これにより機能開発と並行して移行作業を段階的に進められました。

特にpresentation層は作業単位として新設するController単位（基本的にはリソース単位）を想定していましたが、1PR/セッションで移行しきるには困難がありました。

1. フロントエンドも含めた変更が必要なため、リリースタイミングの分割は避けられなかった。
2. 注意すべき観点が多く、1セッションでまとめるとAgentのコンテキストが肥大しすぎる。
3. 新規APIの構成に関する設計判断が必要になる箇所があり、全体が自走してから違和感に気づくと手戻りが大きい。

そのため、以下のような形で「1つのControllerを移行しきる作業」をskills構成としては3段階に分割することで、人間のチェックポイントを設けながら進めました。

* STAGE1: 新APIとして移行する対象の確定 + 旧APIのリファクタリング
  * 具体的には以下のような作業から成ります。
    * スコープの確定
    * 旧API由来の生成コードへの依存をpresentation層に留めるようリファクタ
    * Controllerに載っていたビジネスロジックをusecaseとして切り出し
    * 移行不要な（利用されていない）APIの刈り取り（ `@Deprecated` の付与）
  * レビュアーは対象リソースに関する依存がusecase以降の層に残っていないこと、presentation層がusecaseの呼び出しのみになっていること等を観点に受け入れを行ないます。
* STAGE2: 新APIの実装
  * テストの整備を含みます。旧APIでビジネスロジックのテストをController経由の統合テストとして実装していた場合は、削除時のカバレッジ低下を避けるため、同等のテストを適切なレイヤーに追加します。
  * レビュアーは新APIのデザイン、API契約の妥当性（Nullability含む）を観点として受け入れを行ないます。
* STAGE3: フロントエンドの呼び出しを新APIに切り替えます。
  * 合わせて移行済みとなったAPIに `@Deprecated` markを付与するところまで行ないます。
    * 削除は機械的であることと、旧実装を確認しながら進めたいケースが想定されたため、後のフェーズに送りました。
  * レビュアーはフロントエンドのハンドリングに想定しない差分が含まれていないかを観点に受け入れを行ないます。

また小さな工夫ですが、このように特定の観点での繰り返しの調査を行なう場合は、定型のフォーマットを作成させる方法が有効に感じました。例えばNullabilityの調査については以下のような形で調査票として記録させることで、Agent自体のヌケモレの検査と人間のレビューに利用することができました。

| フィールド | DB NOT NULL | 集計/JOIN経路 | Entity nullability | DTO nullability | FE 初期値 null | new API Response required | new API Request required |
|-----------|------------|------------|------------------|----------------|-------------|-----------------|-------------------|
| id | YES | - | non-null | non-null | - | YES | - |
| title | YES | - | non-null | non-null | NO | YES | YES |
| labelName | YES (別テーブル) | LEFT JOIN | n/a | @Nullable | - | NO | - |
| memo | NO | - | @Nullable | @Nullable | YES (form) | NO | NO |

:::message
もちろんですが、筆者だけで進めた作業ではありません。
対象のリポジトリではマージ前に 1 approveを必須としていますので、199本のPRをレビューしてくれたチームメンバーが必ずいます。
協力あってのことですので、この場を借りて感謝申し上げます。
:::

## ふりかえり

導入PJ全体の成果のうち、NullAwayの導入作業にかけた工数が占める割合は極めて小さいものでした。それ以外の大半は、曖昧になっていたNullabilityを棚卸して、明らかにし、宣言として定着させる作業でした。

当初の目論見であったレビューコストの削減は期待通りに機能しているように今のところ感じられます。防御的な実装（念のためのnullチェック）は不要になり、もし誤った取り扱いを実装してしまってもマージ前に検出可能な状態となりました。また棚卸しを通じて、OpenAPI specの仕様統一やlintの導入、データライフサイクルに関するドキュメンテーションといった資産を手に入れることができました。

今後の課題として、残った `@Nullable` たちをどうしていくのかは残っています。やりきれなかった型の分離や、テーブル定義自体の見直しなどで、基本的にNullableな項目は減らしていく方向で長期的に取り組む想定です。

## まとめ

JavaにおいてNullの取り扱いは人間にとって難しい要素の1つです。NonNull性が完全に保証できない箇所では安全のためのNullチェックを入れたくなり、またそれを積極的に止めるには意志が必要です。今回、Nullabilityの棚卸しを行なって判断に根拠を持たせ、その判断をNullAwayを用いて固定しました。これにより意志に頼らずとも、必要最小限のNullチェックだけをコンパイル時に要求されるようになりました。

NullPointerExceptionに嫌な思い出があり、仕組みで解きたいと考えている方の一助になりましたら幸いです。
