## これはなに

Nstock株式会社でソフトウェアエンジニアをしているnonoです。
主に携わっているNstock株式報酬のバックエンドサービスにNullAwayを導入したのでその話をします。


## プロダクトのテクノロジースタック/パッケージ構成

* Java25
* SpringBoot 4
* Maven

またパッケージ構成としては、部分的にfeatureパッケージを導入したレイヤードアーキテクチャとなっています。
presentation/usecase層はプロジェクトグローバルにあり、domain/infrastructureは機能別のパッケージにwrapされています。

## NullAwayとは？何故今入れるのか

NullAwayはUberが開発したErrorProneプラグインです。
アノテーションベースに静的解析を行い、 `@Nullable` が付与されていない変数・引数へのNullの代入をコンパイル時点で検出できます。
適切に運用することで、実装時のNullに関する考慮を大幅に減らすことができます。

## 導入計画

### 簡単に入れるには？何故それは使えないのか？

基本的にはpom.xml（またはbuild.gradle）にNullAwayとErrorProneの設定を追加すれば動作します。

```
<dependencies>
  <dependency>
    <groupId>org.jspecify</groupId>
    <artifactId>jspecify</artifactId>
    <version>1.0.0</version>
  </dependency>
  <dependency>
    <groupId>com.google.errorprone</groupId>
    <artifactId>error_prone_core</artifactId>
    <version>2.36.0</version>
    <scope>provided</scope>
  </dependency>
  <dependency>
    <groupId>com.uber.nullaway</groupId>
    <artifactId>nullaway</artifactId>
    <version>0.12.15</version>
    <scope>provided</scope>
  </dependency>
</dependencies>

<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
      <configuration>
        <fork>true</fork>
        <annotationProcessorPaths>
          <path>
            <groupId>com.google.errorprone</groupId>
            <artifactId>error_prone_core</artifactId>
            <version>2.36.0</version>
          </path>
          <path>
            <groupId>com.uber.nullaway</groupId>
            <artifactId>nullaway</artifactId>
            <version>0.12.15</version>
          </path>
        </annotationProcessorPaths>
        <compilerArgs>
          <!-- Error Prone を動作させるための JVM export 設定（Java 21 以降で必要） -->
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.api=ALL-UNNAMED</arg>
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.file=ALL-UNNAMED</arg>
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.main=ALL-UNNAMED</arg>
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.model=ALL-UNNAMED</arg>
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.parser=ALL-UNNAMED</arg>
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.processing=ALL-UNNAMED</arg>
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.tree=ALL-UNNAMED</arg>
          <arg>-J--add-exports=jdk.compiler/com.sun.tools.javac.util=ALL-UNNAMED</arg>
          <arg>-J--add-opens=jdk.compiler/com.sun.tools.javac.code=ALL-UNNAMED</arg>
          <arg>-J--add-opens=jdk.compiler/com.sun.tools.javac.comp=ALL-UNNAMED</arg>
          <!-- Error Prone に必要なコンパイラポリシー設定 -->
          <arg>-XDcompilePolicy=simple</arg>
          <arg>-XDshould-stop.ifError=FLOW</arg>
          <!-- NullAway のみを有効化し、jp.nstock.backend 配下を解析対象にする -->
          <arg>-Xplugin:ErrorProne -XepDisableAllChecks -XepOpt:NullAway:AnnotatedPackages=jp.nstock.backend -XepOpt:NullAway:JSpecifyMode=true -Xep:NullAway:ERROR</arg>
        </compilerArgs>
      </configuration>
    </plugin>
  </plugins>
</build>
```

またはmaking氏の (nullabity-maven-plugin)[https://github.com/making/nullability-maven-plugin]を利用する方法もあります。
※ 私たちは2025/11頃から設定を入れ始めていたのでタイミング合わず

### ゴールを何処に設定するか

NullAway + ErrorProneの構成では、パッケージ単位で段階的にNullAwayの導入を進めることができます。
```xml
<!-- OnlyNullMarked=true: @NullMarked が付いたパッケージだけをチェック対象にする -->
<arg>-Xplugin:ErrorProne -XepDisableAllChecks -XepOpt:NullAway:OnlyNullMarked=true -XepOpt:NullAway:JSpecifyMode=true -Xep:NullAway:ERROR</arg>
```
```java
/**
 * 事務局アカウント管理のドメイン層。
 * <p>
 * リポジトリインターフェース、ドメインサービスインターフェースを配置する。
 */
@NullMarked
package jp.nstock.backend.command.admin_account.domain;

import org.jspecify.annotations.NullMarked;
```
これにより、NullAwayを何処まで入れるのか、という意思決定が可能になります。

方針の候補は以下の2つでした。
1. コアドメインにのみ導入する
2. プロジェクト全体を対象とする

1はROIベースでは良好な選択肢と言えるでしょう。変更頻度が高く、重要な箇所にのみ絞って導入する。一方で、私たちは2の方針で進めることとしました。
決めてはレビューコストの観点でした。

Nullabilityはレビュー時にトレースすべき値の範囲の候補を増やします。コードの変更が低廉化した現代において、受入のコストを下げる価値は高まっていると考えました。
また部分的な導入は、その境界を意識したレビューが必要になります。これはレビューの認知負荷を高める方向に働き、望ましくないと判断しました。

### 具体的な方針の検討

NullAwayをいきなりプロジェクト全体に適用するのは現実的ではありませんでした。
導入時点で `@NonNull` `@Nullable` のようなアノテーションは部分的に設定されていましたが完全ではありませんでした。
この状況で設定を導入すると、まず「見過ごされていたがNullableな値をNonNullに渡そうとしている」箇所がコンパイルで落ちます。
当時の環境でプロジェクト全体に設定を適用した場合を実測すると、520箇所、155ファイルでコンパイルエラーが発生しました。

コンパイルを通すためには値の出元をNonNullでアノテーションするか、`Objects.requireNonNull` で囲うかしてNonNullを保証する必要があります。
値が一貫してNonNull保証できるなら簡単ですが、ユースケース固有のNonNull性であれば `Objects.requireNonNull` が必要であり、調査に誤りがあれば実行時エラーとなります。
NonNullを保証できる型とNullableな型を同じClassで取り扱うことがそもそも不適切で、分離すべきという箇所もあるでしょう。

また設定済みのNonNull, Nullableが何処まで信用できるのか、という問題もあります。
当初の想定ではNonNullだったが、機能拡張の過程でNullを取り扱う経路が増え、アノテーションがメンテナンスされていないケースもありえます。

そのため大方針としては、Nullabilityの確かな根拠を持てる箇所から段階的に導入していくことにしました。
具体的には、infrastructure -> presentation -> 中間層の順です。
※ 実際には特定のコア機能を代表値としてinfrastructure -> presentation -> 中間層の流れを通して妥当性と効果検証を行い、また作業手順をskills化してから横展開をしています。

## 導入実践

### infra層の実装

infrastructure層から着手した理由はシンプルで、実装の大半がDBアクセスであり、そこにはDBスキーマという強力なNonNull性の根拠があるためです。
カラム定義にdefaultを設定していない場合、not null制約が設定された列の参照/書き込みは確実にNonNullであると言えます。
対象プロジェクトではSpringDataJDBCを利用しており、 `@Table` を用いてテーブルと紐づくDTOを作成して持ち回る実装が大半を占めていました。
これにより、infrastructure層のDTO群のNonNull/Nullableは確度高く整備できました。

部分的に考慮が必要だったのは外部結合によりNullabilityが発生しうるケースです。
これは機械的には判断できないため、個別データのライフサイクルからNullが正常系であり得るかデータ不整合の異常系かの整理をつけていく作業が必要でした。

### presentation層の実装

presentation層は主にWebAPI実装を行っています。対象プロジェクトではOpenAPI Specification + OpenAPI Generatorを用いて開発をおこなっていました。
specにはrequiredを付与していましたが、歴史的経緯からあまり信頼しきれない状態となっていました。
またNullAwayとは別の文脈ですが、既存のspecの構成に課題が溜まっている状態でした。

1. ControllerClassの単位として1階層目の高さでの分割を選んでいたため、配下に多くのエンドポイントを抱えるControllerが肥大していた（最も肥大したコントローラのテストクラスで15k行近く）
2. 歴史的経緯から記法がブレている。requiredの設定方針、exampleの有無、Enumの定義位置 etc.
3. OpenAPI specで定義したEnumがpresentation層以外でも利用されており、FEの表現幅とドメインの表現幅（場合によってはDBの表現幅）が乖離できない箇所があった

上記が積もり積もったこともあり、NullAway対応を契機にAPIを全て作り直すこととしました。
具体的には以下のような仕組みを整備した上で、個別エンドポイントの移行を順次進めました。
1. OpenAPIの記法についてガイドドキュメントを整備。合わせてマージ前に検証を行なうCIをspectralを用いて実装。
2. 新規specの生成物の配置先にpackage-info.javaを配置してNullAway対象化
3. 新規specの生成物の配置先に対する依存をpresentation層からのみ許可するようArchUnitのRule整備

これにより、新規の生成物の記法を揃えつつ、NullAwayの検証を成立させつつ、ArchUnitで弾かれる箇所を修正することで求める状態に近づけられるようガードレールを敷きました。
そのうえで個別エンドポイントについてフロントエンドのハンドリングを調査しながら、Nullが設定されうる箇所のみrequiredを外す、という地道な移行を行いました。

### 中間層の詰め

presentation層とinfrastructure層のNullabilityが定まれば後は概ね挟み込みです。
読み込みにせよ書き込みにせよ、inとoutのNullabilityが既に保証されているため、整合するように必要な箇所にアノテーションを付与していく作業となります。
また関数内で新たな値を作り出す箇所のNullabilityの調査は比較的狭い範囲の調査で絞り込めます。

### CleanUp

ここまでで各パッケージに対しての整備が完了したので、改めて段階導入の為の仕組みを撤去して作業完了です。
具体的にはpom.xmlの検査範囲変更（ `OnlyNullMarked` の削除）と、薄い記述しか持っていなかった（パッケージに関する説明のない）package-info.javaの削除です。

## ふりかえり

導入PJ全体の成果のうち、NullAwayの導入作業にかけた工数が占める割合は極めて小さいものでした。
それ以外の大半は、曖昧になっていたNullabilityを棚卸して、明らかにし、宣言として定着させる作業でした。

当初の目論見であったレビューコストの削減は期待通りに機能しているように今のところ感じられます。
防御的な実装（念のためのnullチェック）は不要になり、もし誤った取り扱いを実装してしまってもマージ前に検出可能な状態となりました。
一方で得られた成果として大きいのはむしろ、OpenAPI specの仕様統一やlintの導入、データライフサイクルに関するドキュメンテーションといった副産物のようにも思います。

今後の課題として、残った `@Nullable` たちを今後どうしていくのかは残っています。
やりきれなかった型の分離や、テーブル定義自体の見直しなどで、基本的にNullableな項目は減らしていく方向で長期的に取り組む想定です。

## まとめ

JavaにおいてNullの取り扱いは人間にとって難しい要素の一つです。
NonNull性が完全に保証できない箇所では安全のためのNullチェックを入れたくなり、またそれを積極的に止めるには意志が必要です。
今回、NullAwayを用いてNullに関する規約・考え方を仕組みとして固定する方法を取りました。

NullPointerExceptionに嫌な思い出があり、仕組みで解きたいと考えている方の一助になりましたら幸いです。
